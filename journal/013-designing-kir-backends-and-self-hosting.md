# Building Monad #013 — Designing KIR, Backends, and Self-Hosting

A compiler becomes most dangerous at the moment it appears to succeed.

It has accepted the source. It has built a semantic model. It has emitted files that look plausible. The generated project may even compile. Those visible signs encourage a conclusion that the translation was correct.

But generated bytes can hide several different failures. A target convention may have silently erased a source constraint. A backend may have selected one of two conflicting authorities because its data structure could not represent both. A cache may have returned output produced by an older validator. A generator may have written half of an artifact set before crashing. A compiler may rebuild itself while reproducing the same defect at every stage.

Monad cannot treat generation as the point where governance ends. Generation is where semantic knowledge crosses into target-specific, executable, and often destructive forms. The boundary needs more structure, not less.

MSC-CORE-0010 completes the planned architecture of the Monad Specification Compiler by defining four linked obligations:

1. lower the immutable Monad Semantic Graph into a validated Kernel Intermediate Representation;
2. execute target backends through explicit, least-authority contracts;
3. validate and atomically publish generated artifact sets; and
4. describe self-hosting as bounded evidence with named assumptions rather than circular proof.

The governing direction is one-way:

```text
validated immutable MSG snapshot
  -> deterministic lowering and visible loss accounting
validated KIR module set
  -> governed backend execution in staging
candidate artifact set
  -> validation and atomic publication
published artifact set
```

Nothing downstream acquires the authority to rewrite the source semantic graph. KIR is not a second semantic database. A backend is not an adjudicator. A generated file is not canonical knowledge. A compiler that rebuilds itself does not become correct by recursion.

That separation is the central design decision of WC-0003.

## Why the compiler needs KIR

It would be simpler to let every backend traverse the MSG directly. A TypeScript backend could search the graph for services and types, a documentation backend could search for descriptions and relationships, and a policy backend could collect governance claims. This would avoid defining another representation.

It would also distribute the meaning of the compiler across every generator.

Each backend would need to understand graph membership, identity, authority, provenance, partiality, conflicts, lifecycle, applicability, and uncertainty. Each would invent its own lowering rules. Two targets might interpret the same semantic construct differently without recording that divergence. A backend update could change semantic translation and rendering at the same time, leaving no stable intermediate surface to compare.

KIR exists to make that translation explicit.

The Monad Semantic Graph answers what governed knowledge the compiler has accepted for a compilation. KIR answers how the applicable portion of that knowledge has been prepared for downstream generation under a declared lowering contract. A backend then answers how validated KIR becomes candidate artifacts for a particular target profile.

These are different questions and different authority domains.

KIR must therefore be rich enough to carry types, effects, capabilities, dependencies, obligations, partiality, and traceability, but it must remain derived. Its modules identify the source graph and fingerprint that produced them. Their canonical content has separate module and set digests. Their trace maps retain the semantic subjects and lowering rules behind each element. Their completeness state reports whether the result is complete, partial, or unavailable.

That identity separation matters. An MSG graph identity is not an MSG fingerprint. Neither is a KIR module identity, KIR content digest, target-profile identity, backend identity, artifact identity, artifact digest, compilation-manifest digest, or run identity. A new backend may produce different artifacts without changing KIR. A new lowering rule may change KIR even when the MSG is unchanged. A path-layout change may change artifact identity without changing semantic meaning.

Using one convenient hash for all of these would make the system unable to say what actually changed.

## Lowering is a recorded semantic decision

The word *lowering* can sound mechanical: turn a high-level construct into a lower-level construct. In Monad, it is a governed semantic decision.

Consider a graph that says a service is subject to two policy claims from different authorities, and that those claims currently conflict. A target format may be able to express both claims. Another may support only one policy reference. A third may have no representation for policy governance at all.

The compiler cannot let each backend improvise. It must record one of five dispositions for every applicable construct:

- **preserved** — the meaning is represented in KIR;
- **deferred** — the meaning remains an explicit downstream obligation;
- **approximated** — a visible, governed approximation is permitted;
- **omitted** — the target profile permits omission and the loss is recorded; or
- **unsupported** — no conforming translation exists and the affected output is unavailable.

The important property is not that every target can express everything. That is unrealistic. The important property is that the compiler never converts a target limitation into a silent change of canonical meaning.

If conflict cannot be represented, the result may be unavailable or explicitly review-only. If an approximation is acceptable, its policy, scope, and consequences must be visible. If provenance or a security obligation cannot survive translation, the compiler must diagnose that fact. Backend convenience is never permission to choose a winning authority.

Lowering rules therefore need identities, versions, input patterns, preconditions, precedence, preserved invariants, possible losses, diagnostics, and compatibility revisions. When two rules apply, resolution cannot depend on registration order, filesystem enumeration, or thread scheduling. Ambiguity that can change meaning is itself a diagnostic.

This design also gives incremental compilation a trustworthy boundary. The compiler can observe the MSG fingerprint, lowering rule set, KIR schema, target profile, semantic options, and every external obligation on which the lowering result depends. When one changes, the affected KIR is invalidated. When dependency completeness is uncertain, coarse recomputation remains correct. Stale precision is not an optimization.

## Canonical KIR is a comparison surface

KIR is useful not only because backends need input. It gives the compiler a canonical point at which to ask whether semantic translation was stable before target rendering began.

Equivalent governed inputs must produce canonically equivalent KIR regardless of traversal order, module scheduling, memory layout, locale, clock, worker identity, or absolute workspace path. Canonical encoding must govern field order, collection order, normalization, number and string representation, unknown fields, schema evolution, and digest domains.

Decoded or cached KIR is not trusted merely because it has the right filename or digest key. It must pass schema compatibility, referential integrity, import/export closure, type, ownership, effect, capability, obligation, trace, ordering, and digest validation before a backend can consume it.

This allows failures to be localized. If two runs agree on the MSG but disagree on KIR, the defect belongs to lowering or its declared inputs. If they agree on KIR but disagree on artifacts, the defect belongs downstream—in profile resolution, backend execution, validation inputs, environment, or publication. Without KIR, those two classes of defect collapse into one opaque generator failure.

KIR is therefore a diagnostic and reproducibility surface as much as an implementation representation.

## Target profiles state the truth about a target

A target is more than a backend name. It has semantics, capabilities, unsupported features, required validators, logical path rules, permitted tools, publication policy, and reproducibility limits.

Monad represents these as immutable, versioned target profiles. A profile participates in the compilation manifest, dependency observations, invalidation, cache compatibility, and reproducibility record because changing the profile can change the result even when the MSG and KIR do not.

This prevents an easy form of accidental dishonesty. Suppose a target language cannot express one ownership constraint. The profile cannot declare that the constraint no longer matters. It can declare the target unsupported for that input, require a review-only approximation, or define a visible auxiliary artifact that preserves the obligation. Canonical graph meaning remains unchanged.

Profiles also prevent implicit environment from becoming part of generation. If a backend depends on a formatter, template bundle, runtime support package, platform feature, or environment variable, that dependency must be declared and observed. An undeclared tool found on one developer's machine cannot quietly influence canonical output.

## A backend generates bytes; it does not grant authority

Plugin systems often make discovery equivalent to authority: a component registers itself, receives a rich process environment, and writes output wherever the host tells it. Monad needs a narrower contract.

A backend declares its stable identity, implementation digest, supported protocol and KIR versions, target-profile range, capabilities, external tools, artifact kinds, diagnostic namespace, isolation needs, and reproducibility limitations. Selection occurs from a canonical candidate set using explicit compatibility and policy. Plugin load order, network timing, and “last registration wins” cannot choose the implementation.

The logical protocol separates four acts:

```text
describe -> plan -> generate -> validate
```

That separation exposes decisions that would otherwise hide inside one generator function. Planning records which target units will be generated, reused, unavailable, or skipped and why. Generation writes only candidate output to an assigned staging area. Validation examines the complete candidate set. Publication remains a separate compiler and governance decision.

The backend receives immutable KIR. It cannot mutate the MSG, compilation manifest, another backend's candidate set, or the accepted KIR. Filesystem writes are confined to staging. Network access, subprocesses, secrets, clocks, randomness, and environment reads are denied unless the profile declares and governs them.

This is not an assertion that the first implementation will have perfect isolation. MSC-CORE-0010 explicitly allows a local bootstrap profile with documented limitations. The non-negotiable requirement is honesty: capabilities and weaknesses are declared, undeclared authority is denied where supported and detected by conformance tests, and unsupported security claims are not implied.

A backend may produce valid bytes. That still does not authorize publication.

## Cache hits return candidates, not truth

Entry #012 established that reusable results remain derived and that clean compilation is the correctness oracle. The backend layer extends that rule.

A backend cache key or compatibility envelope must account for the KIR digests, target profile, backend implementation, protocol, semantic options, validators, external tools, templates, runtime support, artifact layout, and reproducibility-relevant environment. Any output-affecting dependency must be observed or conservatively force regeneration.

Even a compatible cache hit returns an untrusted candidate set. Integrity, provenance, tenancy, layout, target validation, diagnostics, and publication policy still apply. A cached artifact cannot skip secret scanning because it passed last week. It cannot overwrite a user file because its content digest is familiar. It cannot become authoritative knowledge because recomputation is expensive.

This rule keeps caching observationally transparent. Cold, warm, partially populated, evicted, corrupt, malicious, incompatible, and cross-tenant cache states must either fail safely or yield the same governed result as a clean compilation. Cache state may change cost. It may not change meaning or availability.

## Candidate artifacts are not published artifacts

The distinction between candidate and published artifacts is as important as the distinction between KIR and MSG.

Each candidate needs a logical identity, canonical logical path, artifact kind, media type, content digest, producing target and backend, KIR dependencies, provenance, source map, permissions intent, validation state, and taint disposition. Host-absolute paths cannot define artifact identity. Two candidates resolving to the same logical path are a collision unless a target profile supplies a deterministic merge rule.

Before publication, the complete set passes the applicable validation stages:

1. manifest and digest validation;
2. path, collision, size, and permission validation;
3. target syntax or schema validation;
4. target semantic or type validation;
5. source-map and provenance validation;
6. policy, security, and secret scanning;
7. deterministic-regeneration comparison where required; and
8. artifact-set completeness validation.

Only then can publication occur, atomically, at the artifact-set boundary defined by the profile.

Atomicity is a semantic requirement, not merely filesystem polish. Imagine a backend generates an API schema, client library, policy bundle, and deployment manifest. If it replaces the first two files and crashes before the remaining two, the repository now describes two incompatible worlds. Every individual file may be well formed, yet the set is false.

Monad therefore requires failed, cancelled, incomplete, or unvalidated sets to leave the prior accepted set intact or cleanly recoverable. Existing user-authored files cannot be overwritten without explicit policy and a matching precondition digest. A stale precondition fails; it does not invite last-writer-wins behavior.

The immutable output manifest records what was actually accepted: artifact identities and digests, source MSG fingerprint, KIR digest, target and backend identities, validator results, diagnostics, availability, reproducibility evidence, and publication authority. It makes the published set attributable without turning generated output into semantic truth.

## Traceability must remain many-to-many

Generated content rarely has one source.

A single line in a deployment artifact may combine a service declaration, a security policy, an environment profile, a naming rule, and a backend convention. Conversely, one semantic subject may affect dozens of generated files. A source map that forces every region to name one source would fabricate certainty.

Monad therefore requires bidirectional, many-to-many traceability:

- MSG subjects and lowering rules to KIR elements;
- KIR elements and backend rules to artifact regions;
- diagnostics to the subjects and stages they concern; and
- source changes to the artifacts they can invalidate.

Trace data may be embedded or stored in sidecar artifacts, depending on target behavior and information-disclosure policy. Its job is to make translation explainable and invalidation auditable, not to expose protected knowledge indiscriminately.

This trace chain is especially important for AI-assisted development. An AI may propose a lowering rule, backend implementation, fix, or explanation. It may not use fluent output as evidence that a semantic loss was acceptable, that a diagnostic should be suppressed, that candidate artifacts should be published, or that self-hosting succeeded. Those are governed dispositions tied to recorded evidence and accountable authority.

## Self-hosting is an evidence ladder

Self-hosting has symbolic power. A language or compiler appears mature when it can build itself. That milestone is real, but its meaning is often overstated.

If compiler A contains a defect and uses that defect to build compiler B, then B may reproduce it when building compiler C. B and C can be byte-identical and still be wrong. Worse, a compromised bootstrap compiler can inject behavior not present in visible source and teach descendants to reproduce it. Repetition proves stability under assumptions; it does not create correctness from nothing.

Monad treats self-hosting as a campaign with named stages:

- **Stage 0** is the trusted bootstrap compiler or toolchain, including its provenance and assumptions.
- **Stage 1** is produced from governed MSC inputs by Stage 0.
- **Stage 2** is produced from the same governed inputs by Stage 1.
- **Comparison** evaluates Stage 1 and Stage 2 on declared surfaces.

Stage numbers describe lineage, not trust rank. Stage 2 is not automatically more correct than Stage 1.

The comparison must also name its level. Monad distinguishes semantic agreement, canonical KIR agreement, logical artifact agreement, byte equality, governed behavioral agreement, and diverse-path agreement. Passing one cannot be reported as passing another.

For example, two stages might produce different binaries because of normalized build metadata while agreeing semantically, behaviorally, and at the logical artifact level. That is not byte reproducibility. Conversely, byte-identical binaries may still share a semantic defect. The evidence is meaningful only when the comparison surface is stated precisely.

Every campaign records source and specification digests, Stage 0 provenance, compiler and environment identities, manifests, MSG and KIR identities, target and backend identities, validator versions, cache policy, diagnostics, availability, comparison levels, exclusions, first known divergence, conformance results, taints, waivers, risks, and approving authority.

At least one acceptance comparison must be clean and independent of reusable cache state. A release-grade claim should also include diverse double compilation—an independently implemented or derived path—or explicitly record why that evidence is unavailable. Missing diversity is a limitation, not a success hidden in a footnote.

The resulting claim is deliberately bounded: under these inputs, tools, environment assumptions, comparison rules, and tests, these stages agreed at these levels. That is far more useful than the unqualified statement “Monad is self-hosting.”

## The bootstrap profile must be small but honest

Monad does not need every advanced capability before implementing the first trustworthy path. The bootstrap profile may use one KIR schema, coarse invalidation, local-process backends, a small target set, local verified caches, deterministic layouts, and staged self-hosting without byte-identical native binaries.

What it cannot omit are the boundaries that make later refinement safe: immutable validated KIR, visible semantic loss, structured diagnostics, deterministic generation, complete dependency observation at the declared granularity, safe cache rejection, candidate validation, atomic publication, output manifests, and reproducibility records.

This is a recurring Monad principle: coarse but correct is a valid starting point. Fine-grained but incomplete is not.

A whole-graph lowering pass may be slower than an ideal incremental engine, but it can be checked against clean results. A local backend sandbox may have documented limitations, but those limitations can be tested and improved. A small set of target profiles may constrain adoption, but it avoids pretending that unknown targets preserve meaning.

The bootstrap system earns expansion by producing evidence at its declared boundary.

## Seven work packets turn the design into an implementation path

MSC-CORE-0010 is still a specification. The implementation decomposition continues the global MSC sequence with seven planned, unassigned packets.

**WP-MSC-0014 — Kernel Intermediate Representation** establishes the immutable module model, canonical encoding, identity domains, compatibility rules, validation pipeline, and deterministic fixtures. It creates the representation boundary that every later WC-0003 packet consumes.

**WP-MSC-0015 — Deterministic MSG-to-KIR Lowering** implements versioned lowering rules, explicit preservation and loss dispositions, trace maps, dependency observations, target readiness, partiality, and deterministic decision records. It is responsible for proving that target preparation does not silently rewrite graph meaning.

**WP-MSC-0016 — Target Profiles and Governed Backend Protocol** implements profile resolution, canonical backend discovery, capability negotiation, invocation, isolation, failure behavior, and structured backend diagnostics. It holds the line between generating candidate bytes and authorizing publication.

**WP-MSC-0017 — Backend Planning, Invalidation, and Verified Reuse** extends the MSC-CORE-0009 trust system across KIR, profiles, backends, validators, templates, tools, layouts, and environment contracts. It must demonstrate that every cache condition either matches the clean oracle or fails safely.

**WP-MSC-0018 — Artifact Validation and Atomic Publication** defines candidate and output manifests, source maps, collision and overwrite protection, validation stages, transaction boundaries, rollback, and recovery. It is where generated output becomes an accepted artifact set without becoming canonical semantic knowledge.

**WP-MSC-0019 — Bootstrap and Bounded Self-Hosting Evidence** implements campaign records, Stage 0/1/2 lineage, level-specific comparisons, clean campaigns, divergence reporting, diverse-path evidence, and explicit trust limitations. It cannot accept circular reproduction as proof.

**WP-MSC-0020 — End-to-End Conformance Suite** attacks the entire boundary: semantic loss, ambiguity, stale reuse, backend leakage, nondeterminism, malicious output, path attacks, secret leakage, interrupted publication, false comparison claims, and incomplete trust records. It closes implementation evidence only after the preceding packets have accepted implementations.

The dependency graph is intentionally staged. KIR precedes lowering and backend consumption. Backend planning and reuse depend on the compiler-wide diagnostic and incremental contracts. Publication consumes candidate output only after backend and cache boundaries are known. Self-hosting consumes validated, reproducible artifact behavior. Adversarial conformance tests the assembled system.

None of those implementations is claimed by writing the packets.

## What WC-0003 can and cannot establish

WC-0003 can establish that the final downstream compiler boundary is coherent and implementation-ready. It can confirm that MSC-CORE-0010 has explicit owners for KIR, lowering, target profiles, backend execution, reuse, publication, self-hosting, and conformance. It can test the planning decomposition for gaps, cycles, boundary violations, and unowned normative requirements.

It cannot establish that KIR exists, that a backend has run, that publication is atomic, that a compiler has rebuilt itself, or that any self-hosting comparison passed. Those claims require production code, executable tests, validation records, campaign evidence, and packet-specific acceptance.

WC-0003 also cannot close PI-002 by itself. The increment still requires a direct-source consistency review across MSC-CORE-0008, MSC-CORE-0009, and MSC-CORE-0010. That review must confirm that the MSG remains authoritative, identity domains agree, target readiness does not rewrite graph meaning, diagnostics and caching extend consistently, partial and cancelled states cannot become published completion, and self-hosting records distinguish every relevant run, manifest, graph, KIR, artifact, and compiler identity.

The architecture freeze remains intact because the design preserves the accepted direction of authority. A reverse KIR-to-MSG path, target-dependent canonical graph, silent semantic loss, nondeterministic backend selection, weakened cache validation, partial publication presented as complete, or self-reproduction treated as proof would require specification amendment rather than an implementation shortcut.

## The final boundary is restraint

The visible purpose of a compiler backend is to create things. The deeper purpose of this design is to constrain what creation is allowed to mean.

KIR makes semantic translation inspectable. Loss accounting makes target limitations visible. Target profiles make compatibility and environment explicit. Least-authority backends prevent generators from becoming governors. Candidate validation and atomic publication prevent plausible fragments from masquerading as a coherent result. Traceability makes outputs explainable. Reproducibility makes changes comparable. Bounded self-hosting records maturity without manufacturing authority from circularity.

The result is not a promise that Monad has already built a self-hosting compiler. It is a contract for recognizing one responsibly.

That distinction completes the design arc of PI-002. The MSG defines governed semantic knowledge. Diagnostics, manifests, invalidation, caching, and reproducibility define how compilation can be observed and safely reused. KIR, backends, publication, and self-hosting define how knowledge can become target artifacts without losing its lineage or exceeding its authority.

The next step is to review whether MSC-CORE-0010 and WP-MSC-0014 through WP-MSC-0020 form a complete, coherent construction plan. Only after that review and the final cross-specification reconciliation can Monad decide whether the compiler implementation threshold is ready to open.
