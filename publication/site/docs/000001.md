## Decision: use Fumadocs

Fumadocs is the best fit for the Monad Engineering Log.

I would **not** replace it with Starlight, Docusaurus, or Fumapress. Monad needs more than a conventional documentation site: it needs a custom publication, chronological engineering journal, architectural reference, artifact registry, document graph, and eventually AI-readable and printable editions.

Fumadocs gives us the strongest balance of:

* Flexible React/Next.js composition
* Type-safe Markdown and MDX collections
* Custom frontmatter validation
* Multiple content collections and workspaces
* Generated page trees and navigation
* Self-hosted search
* AI-readable documentation endpoints
* OpenAPI integration for later Monad APIs
* Custom layouts without abandoning a mature documentation foundation

Fumadocs currently supports multiple React frameworks, but its documented Next.js setup is the most mature path for the amount of customization we need. Its manual installation presently targets Next.js 16 and Tailwind CSS 4. ([Fumadocs][1])

# Selected stack

```text
Framework:          Next.js 16 App Router
Documentation:      Fumadocs Core + Fumadocs UI
Content compiler:   Fumadocs MDX
Language:           TypeScript, strict mode
Styling:            Tailwind CSS 4 + CSS custom properties
Package manager:    Bun
Search:              Orama, self-hosted initially
Validation:          Zod
Code formatting:     Biome
Testing:             Vitest + Playwright
Deployment:          Static-capable, with server deployment supported
Primary content:     Markdown and MDX
```

Fumadocs MDX exposes type-safe collections, generated tables of contents, structured search data, extracted references, and build-time frontmatter validation. ([Fumadocs][2])

Orama is the default Fumadocs search implementation and can run through a server endpoint or a statically generated search index, allowing us to begin without a paid hosted search service. ([Fumadocs][3])

## Why not the alternatives?

### Fumapress

Fumapress offers easier automatic routing, `llms.txt`, MCP, and other conveniences, but it imposes its own Vite/Waku-based framework conventions. That is useful for ordinary docs sites, but Monad needs deeper control over routing, data relationships, custom visualizations, and derived publications. ([Fumadocs][4])

We should use the lower-level, more composable Fumadocs stack.

### Astro Starlight

Starlight would be my second choice. It is excellent for a mostly static, content-first documentation site and supports Markdown, MDX, and Markdoc. ([Starlight][5])

However, the Monad site will benefit from React-based interactive features such as:

* Artifact relationship explorers
* Development timelines
* Specification status dashboards
* Architecture graph views
* Search filters
* Article progress and reading paths
* Repository-state displays
* Interactive code and terminal components

Fumadocs gives us a better base for those features.

### Docusaurus

Docusaurus is compelling when conventional product-documentation versioning is the dominant requirement. It has a mature document-versioning workflow that copies documentation into version-specific directories. ([Docusaurus][6])

Monad’s material is not primarily a set of duplicated product manuals. It is a continuously evolving knowledge system where documents, decisions, specifications, and journal entries must remain connected. We should build semantic version views later rather than organize the entire publication around copied version directories.

# Canonical-content architecture

I recommend a **content adapter layer** rather than making the publication site’s internal directory the canonical home of every document.

```text
monad/
├── adrs/
├── architecture/
├── build-log/
├── engineering/
├── journal/
├── knowledge/
├── research/
├── specifications/
│
└── publication/
    └── site/
        ├── app/
        ├── components/
        ├── lib/
        ├── public/
        ├── scripts/
        ├── styles/
        ├── tests/
        ├── content.config.ts
        ├── source.config.ts
        ├── next.config.mjs
        ├── package.json
        └── tsconfig.json
```

The site will use multiple typed collections or collection adapters because current Fumadocs MDX treats each collection as a single content directory. Multiple collections and workspaces can then be merged into one source tree. ([Fumadocs][9])

## Generated-content boundary

Some of the documents created in the other chat may initially lack website-specific frontmatter or navigation metadata. We will not force the article-writing process to become tightly coupled to the website.

Instead, the site will include an ingestion process:

```text
Canonical Markdown
        │
        ▼
Content discovery
        │
        ▼
Filename and identifier validation
        │
        ▼
Frontmatter normalization
        │
        ▼
Relationship extraction
        │
        ▼
Generated Fumadocs collections
        │
        ▼
Site, search, feeds, PDFs, and AI outputs
```

The generated mirror will be disposable and excluded from version control. The original files remain authoritative.

This gives us several advantages:

* Existing Markdown stays readable on GitHub.
* The other writing workstream does not need to know Fumadocs internals.
* Navigation can be generated from document identifiers.
* Missing metadata can produce actionable build errors.
* Cross-references can be validated.
* One document can participate in several indexes without being duplicated.
* We can change site frameworks later without rewriting the source corpus.

# Content-to-route mapping

The initial mapping will be:

| Canonical source  | Website section              |
| ----------------- | ---------------------------- |
| `journal/`        | `/building-monad/`           |
| `architecture/`   | `/system/architecture/`      |
| `adrs/`           | `/artifacts/decisions/`      |
| `specifications/` | `/artifacts/specifications/` |
| `engineering/`    | `/artifacts/engineering/`    |
| `research/`       | `/artifacts/research/`       |
| `knowledge/`      | `/artifacts/knowledge/`      |
| `build-log/`      | `/project/build-log/`        |

The route structure will be independent of physical file placement. That prevents repository organization from becoming accidental public information architecture.

# Site-specific metadata

The ingestion system will recognize metadata such as:

```yaml
id: MJ-0001
title: Building Monad
subtitle: Establishing the Knowledge Engine Core
kind: journal-entry
series: building-monad
series_position: 1
status: published
project_phase: foundation
created: 2026-08-03
updated: 2026-08-03
authors:
  - Thomas Carter
related:
  decisions:
    - ADR-0001
  specifications:
    - MKE-CORE-0001
  articles: []
repository:
  commit: null
  release: null
tags:
  - knowledge-engine
  - architecture
  - foundations
```

Not every canonical file will need to contain every field. The adapter can infer some values from:

* Directory
* Filename
* Document identifier
* Series registry
* Git history
* Relationship registry
