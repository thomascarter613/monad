# WP-AF-0009 — Establish the Monad Architectural Constitution

## Executive Summary

Create the governing architectural constitution for the Monad ecosystem.

The resulting `vision/constitution.md` will define how Monad's architecture, terminology, specifications, subsystem boundaries, compatibility commitments, and engineering processes acquire authority and may evolve.

The Constitution will establish:

* the hierarchy of architectural authority;
* the role of the Manifesto, Principles, Laws, Glossary, Architecture Map, ADRs, and specifications;
* how conflicts among artifacts are resolved;
* which changes require an ADR;
* which changes require specification revisions;
* which changes are editorial;
* how architectural amendments are proposed, reviewed, accepted, implemented, and superseded;
* how emergency changes are handled;
* how compatibility and migration obligations are assigned;
* how provisional architecture becomes accepted;
* how accepted architecture becomes implemented;
* how obsolete architecture is deprecated or superseded;
* how AI-generated proposals participate in governance;
* how self-hosting must preserve human and procedural accountability.

This document is the final primary deliverable of Program Increment PI-001 and completes the Architecture Freeze foundation.

If these questions remain implicit, architecture will drift through implementation convenience, informal discussion, undocumented exceptions, or generated content.

The Constitution must validate and stabilize an authority hierarchy similar to the following.

```text
Monad Laws
    │
    ▼
Architectural Constitution
    │
    ▼
Accepted ADRs and Accepted Normative Specifications
    │
    ▼
Canonical Glossary and Accepted Architecture Documents
    │
    ▼
Accepted Work Packets and Program Increments
    │
    ▼
Implementation and Tests
    │
    ▼
Generated Projections and Documentation
    │
    ▼
Journal, Research, Discussion, and Proposals
```

This hierarchy requires nuance:

* Laws establish foundational invariants.
* The Constitution governs architectural change.
* ADRs decide significant architecture.
* Specifications define normative behavior.
* Glossary and architecture documents clarify canonical structure.
* Work packets authorize bounded execution.
* Implementation must conform to accepted contracts.
* Documentation explains or projects accepted knowledge.
* Research and discussion inform but do not establish authority alone.

# Required Conflict Rules

The deliverable must establish rules equivalent to the following.

## Law Conflict

No accepted artifact may knowingly violate a Monad Law without first amending the Laws through the constitutional amendment process.

## Constitutional Conflict

An ADR or specification that conflicts with the Constitution is invalid until the Constitution is amended or the conflict is removed.

## ADR and Specification Conflict

An ADR records the architectural decision.

A specification defines the resulting normative contract.

If they conflict:

1. the inconsistency must be reported;
2. new implementation must pause where the conflict is material;
3. the accepted architectural intent must be determined;
4. the incorrect artifact must be amended;
5. history must be preserved.

An ADR must not be used as a permanent substitute for a required specification.

## Specification and Implementation Conflict

Accepted specification governs intended behavior.

Implementation divergence must be classified as:

* defect;
* temporary deviation;
* incomplete implementation;
* evidence that the specification requires amendment.

Implementation does not silently override the specification.

## Glossary Conflict

A specification may define a narrower contextual meaning but may not silently redefine a canonical term.

## Documentation Conflict

Documentation and generated projections never override canonical architecture or normative specifications.

## Work-Packet Conflict

A work packet cannot amend architecture by itself.

It must reference the ADR or amendment authorizing architectural change.

# Architectural Change Classification

The Constitution must define change classes.

## Class 0 — Editorial

Examples:

* spelling;
* formatting;
* broken links;
* nonsemantic reordering;
* clearer wording that does not alter meaning.

Requirements:

* ordinary review;
* no ADR;
* no compatibility impact.

## Class 1 — Clarification

Clarifies existing accepted meaning without changing required behavior.

Requirements:

* referenced evidence;
* review against governing artifacts;
* changelog or work-packet record where material.

## Class 2 — Compatible Refinement

Adds precision or capability without invalidating conforming existing behavior.

Examples:

* optional field;
* additive diagnostic metadata;
* new nonrequired projection;
* performance improvement preserving semantics.

Requirements may include:

* work packet;
* specification amendment;
* conformance tests;
* ADR when architectural boundaries change.

## Class 3 — Additive Architecture

Introduces a new subsystem, extension point, representation, service, or architectural capability without intentionally breaking accepted contracts.

Requires:

* architecture analysis;
* ADR;
* responsibility and dependency mapping;
* maturity classification;
* specification plan;
* migration analysis;
* project-status update.

## Class 4 — Behavioral Change

Changes accepted semantics or externally observable behavior.

Requires:

* ADR where architectural;
* specification revision;
* compatibility classification;
* test updates;
* migration or release notes;
* explicit effective version.

## Class 5 — Breaking Architectural Change

Invalidates accepted assumptions, contracts, data, dependencies, identities, or ecosystem integrations.

Requires:

* explicit breaking-change proposal;
* ADR;
* affected specification amendments;
* migration plan;
* deprecation strategy where possible;
* compatibility analysis;
* implementation plan;
* verification;
* major-version impact assessment.

## Class 6 — Constitutional Amendment

Changes architectural authority, governance, foundational precedence, or amendment rules.

Requires the highest review threshold defined by the Constitution.

## Emergency Deviation

A temporary, bounded exception required to address urgent:

* security;
* data integrity;
* legal;
* operational;
* severe correctness concerns.

It is not a permanent change class.

# ADR Requirement Rules

An ADR is mandatory when a change:

1. introduces a first-class subsystem;
2. removes or merges a first-class subsystem;
3. changes a subsystem's primary responsibility;
4. changes canonical dependency direction;
5. changes the canonical semantic representation;
6. changes the MSG/MKE boundary;
7. changes the MSG/KIR boundary;
8. changes local-first guarantees;
9. introduces a mandatory external provider;
10. changes identity, provenance, authority, or lifecycle foundations;
11. introduces a new persistence authority;
12. changes supported compatibility policy;
13. selects a foundational technology with substantial lock-in;
14. reverses an accepted ADR;
15. creates a breaking architectural change;
16. establishes a security trust boundary;
17. changes governance or constitutional interpretation materially.

An ADR is normally unnecessary for:

* editorial changes;
* routine implementation details inside accepted boundaries;
* local refactoring preserving contracts;
* test additions;
* documentation projections;
* ordinary work planning.

---

# Specification Requirement Rules

A specification is required when behavior must be:

* implemented consistently;
* validated;
* tested for conformance;
* consumed by independent components;
* versioned;
* projected into generated artifacts;
* exposed to users or integrators;
* preserved across implementations.

An ADR may authorize the direction.

The specification must define the contract.

# Subsystem Governance

A proposed first-class subsystem must define:

```text
name
full_name
maturity
primary_responsibility
inputs
outputs
consumers
dependencies
prohibited_responsibilities
ownership_boundary
failure_boundary
versioning_boundary
security_boundary
implementation_plan
```

A subsystem may be accepted only when:

1. it has one primary responsibility;
2. no existing subsystem already owns that responsibility;
3. at least one concrete consumer exists;
4. its layer placement is known;
5. its dependency direction is legal;
6. its outputs are distinguishable from existing representations;
7. its introduction reduces ambiguity;
8. its maturity is represented honestly;
9. an ADR authorizes it where required.

A subsystem must not be created merely to provide an acronym for a feature.

---

# Dependency Governance

A new architectural dependency must document:

* source component;
* target component;
* purpose;
* direction;
* runtime necessity;
* build-time necessity;
* optionality;
* failure behavior;
* local/offline effect;
* version compatibility;
* security implications;
* replacement strategy.

Dependency inversions prohibited by the Architecture Map require an ADR and constitutional review.

Circular architectural responsibilities are prohibited.

Runtime bidirectional exchange may exist only through explicit contracts without circular ownership.

# Representation Governance

Changes to major representations require explicit ownership.

## Surface AST

Frontend-owned and source-language-specific.

## Canonical AST

MSC-owned shared compiler representation.

Changes require compatibility and compiler-pass impact analysis.

## MSG

Canonical semantic representation for one compilation snapshot.

Changes require:

* ontology impact;
* MKE impact;
* projection impact;
* migration analysis;
* conformance fixtures.

## MKE Persistent Model

Must preserve MSG meaning and history independently of backend implementation.

## KIR

Derived and target-oriented.

KIR changes must not silently redefine MSG semantics.

## Publication Projection

Derived and noncanonical.

Renderer changes normally do not require architectural amendments unless they alter publication contracts or source-of-truth assumptions.

# Dissent and Alternatives

Architectural governance must preserve disagreement.

An ADR or amendment should record:

* alternatives considered;
* reasons rejected;
* dissenting analysis;
* unresolved concerns;
* evidence that could trigger reconsideration.

Dissent does not block acceptance automatically.

It must not be erased from history.

A rejected proposal may later be reconsidered when:

* assumptions change;
* implementation evidence emerges;
* dependencies change;
* new risks appear;
* earlier constraints disappear.

---

# Emergency Deviations

An emergency deviation may be authorized only to address urgent:

* security vulnerability;
* data loss or corruption;
* legal requirement;
* severe operational incident;
* catastrophic correctness defect.

An emergency deviation must record:

```text
deviation_id
reason
scope
authorizer
affected contracts
temporary behavior
risk
start time or version
expiration
remediation work packet
required retrospective ADR
```

## Emergency Rules

1. Scope must be minimal.
2. Duration must be bounded.
3. The deviation must be visible.
4. It must not silently become permanent architecture.
5. A retrospective review is mandatory.
6. A permanent change requires the ordinary amendment process.
7. Removal or formal adoption must occur before expiration.
8. Security-sensitive details may be access-restricted without removing the existence of the deviation.

# Provisional Architecture

Monad uses maturity states to prevent ideas from becoming accidental obligations.

## Reserved

A name or conceptual area is held for future work.

No implementation obligation exists.

## Provisional

A working architectural concept exists but may change.

It must not be treated as a stable public contract.

## Planned

The responsibility and direction are accepted, but detailed specification or implementation remains incomplete.

## Accepted

The architecture is approved as canonical.

## Implemented

Accepted architecture is realized with evidence.

## Maturity Promotion

Promotion requires:

```text
reserved
  ↓
provisional
  ↓
planned
  ↓
accepted
  ↓
implemented
```

Stages may be skipped only with adequate evidence.

Promotion must be recorded.

Implementation alone does not promote provisional architecture automatically.

# Supersession and Reversal

An accepted architectural decision may be superseded.

Supersession requires:

* replacement decision;
* rationale;
* predecessor reference;
* compatibility impact;
* migration plan;
* effective version;
* affected specification changes;
* historical preservation.

An ADR may be:

* proposed;
* accepted;
* deprecated;
* superseded;
* rejected;
* withdrawn.

A superseded ADR remains part of architectural history.

Reversal must explain why earlier reasoning no longer governs.

Deprecation provides a transition between accepted and removed behavior.

A deprecation should identify:

* deprecated subject;
* replacement;
* rationale;
* introduction version;
* warning behavior;
* compatibility duration;
* migration guidance;
* planned removal boundary;
* exceptions.

Immediate removal is permitted only when required by:

# Risks

## Risk 1 — Governance Overhead

The Constitution may impose excessive process on minor changes.

**Mitigation**

* Use proportional change classes.
* Keep editorial and routine implementation changes lightweight.

## Risk 2 — Founder Bottleneck

Bootstrap acceptance authority may become a permanent bottleneck.

**Mitigation**

* Define explicit future delegation while accurately representing current authority.

## Risk 3 — Artifact Precedence Ambiguity

ADRs and specifications may appear to compete.

**Mitigation**

* Assign distinct roles: ADR decides; specification defines the contract.

## Risk 4 — Constitutional Rigidity

The governance model may make necessary architecture changes too difficult.

**Mitigation**

* Define an amendment process and bounded emergency deviations.

## Risk 5 — Architecture by Implementation

Code may establish behavior before documents are updated.

**Mitigation**

* Require divergence classification and conformance review.

## Risk 6 — AI Authority Confusion

Generated artifacts may be mistaken for accepted architecture.

**Mitigation**

* Require explicit human or governed adoption.

## Risk 7 — Process Without Enforcement

Rules may exist only in prose.

**Mitigation**

* Design metadata and future validation hooks suitable for self-hosting.

## Risk 8 — Premature Organizational Design

The Constitution may assume a team or foundation that does not exist.

**Mitigation**

* Separate current bootstrap authority from future delegation options.
