# WP-AF-0005 — Define the Monad Ecosystem Overview

## Executive Summary

Create the canonical high-level overview of the Monad ecosystem.

The ecosystem overview will define Monad's major architectural layers, subsystems, responsibilities, boundaries, dependency direction, and principal information flows without descending into implementation detail.

The resulting `vision/ecosystem.md` document will answer:

* What is Monad?
* Which major subsystems comprise it?
* What is each subsystem responsible for?
* What does each subsystem consume and produce?
* How do the subsystems depend on one another?
* Which concepts are accepted, planned, provisional, or deferred?
* Where do users, contributors, tools, and external systems interact with Monad?

The ecosystem overview is explanatory rather than normative. Normative behavior remains the responsibility of ADRs and specifications.

---

# Problem Statement

Monad has evolved into a multi-layer engineering knowledge platform with several related subsystem families.

Current architectural concepts include:

* Monad Specification Language;
* Monad Specification Compiler;
* Monad Semantic Graph;
* Monad Knowledge Engine;
* Monad Graph Ontology;
* Monad Publication Language;
* Monad Publication Engine;
* AI-assisted knowledge services;
* execution-oriented projections;
* command-line and interactive applications;
* documentation and publication experiences.

Without a canonical ecosystem overview, these concepts risk becoming:

* inconsistently described;
* incorrectly layered;
* assigned overlapping responsibilities;
* treated as equally mature when they are not;
* introduced into specifications without clear dependencies;
* misunderstood as separate products rather than parts of one platform.

A stable ecosystem overview is required before the architecture map, compiler pipeline, knowledge lifecycle, and architectural constitution can be completed.

---

# Motivation

The Monad Manifesto establishes why Monad exists.

The Engineering Principles establish how Monad should be designed.

The Monad Laws establish the architectural truths that must remain stable.

The Canonical Glossary establishes what the project's terms mean.

The Ecosystem Overview must now establish how the major parts fit together.

This document will provide the first complete, contributor-facing description of Monad as a coherent system rather than a collection of acronyms and specification series.

---

# Objectives

This work packet has the following objectives:

1. Define Monad as one integrated engineering knowledge platform.
2. Establish the major architectural layers.
3. Identify every accepted first-class subsystem.
4. Assign each subsystem exactly one primary responsibility.
5. Define the principal inputs and outputs of each subsystem.
6. Establish allowed dependency direction.
7. Distinguish foundational systems, services, applications, and projections.
8. Distinguish canonical representations from derived representations.
9. Distinguish current architecture from provisional future concepts.
10. Identify external integration boundaries.
11. Define the relationship between repository knowledge domains and runtime subsystems.
12. Provide a stable foundation for the formal architecture map.

---

# Required Outcome

At completion, a contributor should be able to read `vision/ecosystem.md` and understand the whole Monad platform before reading detailed specifications.

The document must make clear that:

* engineering knowledge is Monad's primary concern;
* source artifacts are compiled rather than treated as canonical meaning;
* MSC produces an MSG compilation snapshot;
* MSG represents canonical semantic knowledge for that snapshot;
* MKE persists and evolves semantic knowledge over time;
* downstream publication, AI, analytics, and execution systems consume semantic knowledge through explicit projections;
* repository folders are knowledge domains, not necessarily runtime services;
* subsystem boundaries are intentionally narrow and non-overlapping.

| --------- | ------------------------------------------------------------ |
| MSL       | Express engineering knowledge and specification intent       |
| MSC       | Compile supported artifacts into analyzed semantic graphs    |

# Architectural Invariants

The following invariants must be reflected in the deliverable.

1. Knowledge remains primary over representation.
2. Every major subsystem has one primary responsibility.
3. MSL does not perform compilation.
4. MSC does not become the persistent knowledge store.
5. MSG does not become a storage-product-specific schema.
6. MKE does not replace compiler semantic analysis.
7. Projections do not redefine canonical knowledge.
8. AI-produced conclusions do not become authoritative automatically.
9. Publication remains separate from canonical knowledge.
10. Execution-oriented representations remain derived from semantic knowledge.
11. Repository taxonomy does not automatically define runtime architecture.
12. Cross-layer dependencies flow toward foundational contracts.
13. Core deterministic operation does not require a remote service.
14. Provenance, authority, lifecycle, uncertainty, and conflict remain preserved.
15. Historical knowledge is evolved rather than erased.

# Architectural Impact

## Classification

**Architecture documentation and stabilization.**

This work packet is not intended to introduce a new subsystem or alter accepted core architecture.

It consolidates and clarifies architecture already established through:

* vision work;
* ADRs;
* specifications;
* accepted Architecture Freeze decisions.

## Permitted Changes

The deliverable may:

* clarify subsystem names;
* formalize responsibilities;
* classify maturity;
* identify overlaps or contradictions;
* mark concepts provisional;
* establish layer placement.

## Prohibited Changes

The deliverable must not:

* rename KIR without an ADR;
* declare provisional services implemented;
* reorder accepted compiler stages without specification changes;
* make MKE responsible for compilation;
* make MSC responsible for persistent historical storage;
* treat the documentation site as the canonical knowledge source;
* promote AI inference to authority by default.

# Risks

## Risk 1 — Ecosystem Inflation

Too many provisional concepts may be presented as required first-class subsystems.

**Mitigation**

* Apply the one-primary-responsibility rule.
* Classify maturity honestly.
* Defer concepts without clear near-term consumers.

## Risk 2 — Layer Confusion

Compiler representations, semantic knowledge, persistence, and projections may be conflated.

**Mitigation**

* Define each boundary explicitly.
* Include a canonical-representation comparison table.

## Risk 3 — Repository/Runtime Conflation

Repository directories may be treated as runtime services.

**Mitigation**

* Document repository knowledge domains separately from runtime architecture.

## Risk 4 — Naming Drift

Acronyms introduced during earlier discussion may conflict with accepted terminology.

**Mitigation**

* Use the glossary.
* Preserve uncertain names as provisional.
* Require ADRs for replacements.

## Risk 5 — Premature Commitment

Future concepts may become architectural obligations before their need is demonstrated.

**Mitigation**

* Use maturity classifications.
* Separate accepted direction from implementation commitment.

## Risk 6 — Implementation Delay

Architecture work may continue expanding rather than enabling software.

**Mitigation**

* Restrict this deliverable to ecosystem orientation.
* Defer detailed subsystem design.
* Complete within PI-001 and proceed immediately to the architecture map.
