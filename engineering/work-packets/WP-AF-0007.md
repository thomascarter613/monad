# WP-AF-0007 — Define the Monad Compiler Pipeline

## Executive Summary

Create the canonical architecture-level description of the Monad Specification Compiler pipeline.

The resulting `vision/compiler-pipeline.md` will connect the high-level ecosystem and architecture maps to the detailed MSC specifications by documenting:

* compiler inputs;
* compilation-unit formation;
* artifact discovery and classification;
* frontend selection;
* parsing;
* surface AST construction;
* normalization;
* canonical AST validation;
* declaration collection;
* symbol and ownership construction;
* namespaces, scopes, imports, exports, and aliases;
* reference resolution;
* type, constraint, authority, lifecycle, profile, and compatibility analysis;
* semantic readiness;
* Monad Semantic Graph construction;
* Knowledge Intermediate Representation lowering;
* persistence handoff;
* diagnostics;
* snapshots;
* incrementality;
* reproducibility;
* extension and trust boundaries;
* failure and partial-compilation behavior.

The document must stabilize the accepted compiler flow without duplicating the full normative content of the MSC specifications.

---

# Problem Statement

MSC-CORE-0001 through MSC-CORE-0007 define substantial parts of the compiler architecture, but the project does not yet have one concise document showing how those parts operate as an integrated pipeline.

Without a canonical pipeline document, contributors may misunderstand:

* which phase owns a responsibility;
* which representations exist between phases;
* where compiler barriers occur;
* when input becomes canonical semantic knowledge;
* whether MKE participates in compilation;
* when KIR lowering occurs;
* how partial and failed compilation are represented;
* how diagnostics accumulate;
* how incremental compilation invalidates downstream state;
* which components are deterministic;
* where extensions may participate;
* which outputs are mandatory or optional.

This ambiguity would make implementation planning difficult and could lead to monolithic compiler code, improper phase coupling, or inconsistent intermediate representations.

---

# Motivation

The Architecture Map establishes where MSC sits in the wider ecosystem.

The Compiler Pipeline must now establish how MSC operates internally at the architectural level.

This deliverable will become the bridge among:

* vision documents;
* MSC-CORE specifications;
* implementation work packets;
* source-code module boundaries;
* test architecture;
* diagnostic architecture;
* self-hosting plans.

It must be detailed enough to guide implementation while remaining concise enough to serve as a contributor orientation document.

---

# Objectives

This work packet has the following objectives:

1. Define the end-to-end MSC compilation flow.
2. Identify every major compiler phase and its single responsibility.
3. Define the representation consumed and produced by each phase.
4. Establish immutable or fingerprinted phase barriers.
5. Distinguish frontend-specific work from common compiler work.
6. Distinguish parsing, normalization, binding, resolution, analysis, graph construction, and lowering.
7. Identify mandatory, optional, deferred, and backend-specific phases.
8. Define compiler failure, recovery, partial-result, and blocked-output behavior.
9. Define how diagnostics propagate across phases.
10. Define incremental invalidation boundaries.
11. Define reproducibility inputs.
12. Define extension and plugin participation boundaries.
13. Clarify MSG construction as the canonical semantic output of compilation.
14. Clarify MKE ingestion as a separate persistence operation.
15. Clarify KIR as a derived lowered representation.
16. Provide a stable basis for MSC-CORE-0008 through MSC-CORE-0010.
17. Establish implementation-oriented module and test boundaries without selecting a programming language.

# Compiler Barriers

## Discovery Barrier

Requires:

* roots resolved;
* artifact identities assigned;
* containment relationships known;
* discovery limits applied;
* unavailable required artifacts diagnosed.

## Parse Barrier

Requires:

* every required artifact parsed or explicitly represented as failed/unsupported;
* source locations preserved;
* frontend versions recorded;
* parse diagnostics finalized for the snapshot.

## Canonicalization Barrier

Requires:

* normalized canonical nodes validated;
* unsupported semantics preserved explicitly;
* normalization losses recorded;
* canonical node identities assigned;
* canonical AST frozen or fingerprinted.

## Declaration-Binding Barrier

Requires:

* declarations collected;
* symbol identities assigned;
* ownership represented;
* collisions recorded;
* symbol snapshot frozen.

## Resolution Barrier

Requires:

* scopes and namespaces built;
* imports and aliases classified;
* all required references assigned explicit outcomes;
* ambiguities and conflicts preserved;
* reference snapshot frozen.

## Semantic-Analysis Barrier

Requires:

* type outcomes assigned;
* constraints bound;
* static constraints evaluated where possible;
* authority and lifecycle explicit;
* profiles and features evaluated;
* compatibility results recorded;
* conflicts and readiness assigned;
* semantic snapshot frozen.

## MSG-Construction Barrier

Requires:

* graph nodes and edges validated;
* compiler-only state excluded or explicitly modeled;
* provenance complete;
* graph identity and fingerprint assigned;
* graph snapshot immutable.

## Lowering Barrier

Requires:

* target profile selected;
* required readiness achieved;
* losses and unsupported semantics classified;
* target-specific validations completed;
* KIR snapshot immutable.

# Pass Scheduling Model

The pipeline document must distinguish the following scheduling classes.

## Linear Pass

Runs once after declared dependencies.

Examples:

* artifact classification;
* canonical AST validation;
* final report construction.

## Parallel Map Pass

Runs independently across artifacts, declarations, or graph regions.

Examples:

* parsing independent artifacts;
* local syntax validation;
* some static analyses.

## Dependency-Scheduled Pass

Runs according to a dependency graph.

Examples:

* package imports;
* declaration dependencies;
* type dependencies.

## Fixed-Point Group

Runs repeatedly until stable or bounded failure.

Examples:

* mutually recursive types;
* cyclic type imports;
* monotonic authority propagation;
* compatible cyclic constraints.

## Deferred Pass

Runs only when a dependency or requested output requires it.

Examples:

* backend lowering;
* external evidence checks;
* publication projections.

## Target-Specific Pass

Runs for one backend, profile, or output representation.

Examples:

* Rust code generation;
* documentation rendering;
* deployment-plan lowering.

# Incremental Invalidation Model

The deliverable must define invalidation as dependency-driven rather than file-only.

Examples:

| Change               | Minimum Invalidated State                             |
| -------------------- | ----------------------------------------------------- |
| Source trivia only   | frontend/source mapping where semantically irrelevant |
| Parsed syntax        | surface AST and all downstream dependents             |
| Normalization rule   | canonical AST and all downstream dependents           |
| Declaration identity | symbols, scopes, references, semantics, MSG, KIR      |
| Export surface       | dependent imports and references                      |
| Type declaration     | dependent type and constraint analysis                |
| Authority rule       | dependent readiness, MSG applicability, KIR           |
| Profile selection    | profile-sensitive analysis and outputs                |
| Backend version      | KIR/backend output only where safe                    |
| Ontology version     | MSG construction and all semantic consumers           |
| MKE storage backend  | ingestion layer only if semantic contract unchanged   |

A cached incremental result must remain semantically equivalent to a complete clean compilation under the same inputs.

# Risks

## Risk 1 — Specification Duplication

The vision document may reproduce entire MSC specifications.

**Mitigation**

* Summarize architectural contracts.
* Link to normative specifications for details.

## Risk 2 — Premature Implementation Commitment

The document may accidentally select concrete package boundaries or technologies.

**Mitigation**

* Keep component boundaries language-neutral.
* Defer code organization to implementation work packets.

## Risk 3 — Hidden Phase Coupling

A phase may rely on mutable state owned by another phase.

**Mitigation**

* Require explicit inputs, outputs, snapshots, and barriers.

## Risk 4 — Overly Linear Pipeline

Some analyses require dependency scheduling, parallelism, or fixed points.

**Mitigation**

* Define scheduling classes separately from the conceptual flow.

## Risk 5 — Incorrect Success Semantics

Optional-output failure may be confused with semantic-compilation failure.

**Mitigation**

* Define output availability and atomicity explicitly.

## Risk 6 — Incremental Unsoundness

Cache reuse may produce a result different from a clean build.

**Mitigation**

* Make clean-build semantic equivalence a mandatory invariant.

## Risk 7 — Architecture Expansion

Producing the pipeline may invite new compiler subsystems.

**Mitigation**

* Use accepted MSC responsibilities only.
* Record implementation conveniences as components, not new architectural systems.

# Validation Checklist

## Phase Validation

* Every phase has one primary responsibility.
* Every phase has explicit input and output.
* Every downstream phase consumes a stable snapshot.
* No phase silently owns persistence and publication together.

## Representation Validation

* Source and semantic identity remain distinct.
* Surface and canonical AST remain distinct.
* Symbols and semantic identities remain distinct.
* Reference graph and MSG remain distinct.
* Semantic-analysis snapshot and MSG remain distinct.
* MSG and KIR remain distinct.
* MSG and MKE persistent history remain distinct.

## Failure Validation

* Parse failure is distinguishable from semantic failure.
* Semantic failure is distinguishable from persistence failure.
* Persistence failure is distinguishable from lowering failure.
* Optional-output failure is distinguishable from required-output failure.
* Resource exhaustion is distinguishable from invalid input.
* Internal compiler error is distinguishable from user error.

## Incremental Validation

* Invalidation follows semantic dependencies.
* Negative caches are invalidated when availability changes.
* Version changes participate in cache keys.
* Clean and incremental outputs are semantically equivalent.

## Security Validation

* Untrusted input is bounded.
* Extension execution is governed.
* Network and filesystem access are explicit.
* AI is not required by the deterministic core.
* Evaluators and solvers have limits.
