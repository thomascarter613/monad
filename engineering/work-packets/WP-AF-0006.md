# WP-AF-0006 — Define the Monad Architecture Map

## Executive Summary

Create the canonical visual and structural map of the Monad ecosystem.

The Architecture Map will translate the accepted textual architecture in `vision/ecosystem.md` into a compact, navigable system model showing:

* architectural layers;
* subsystem placement;
* responsibility boundaries;
* dependency direction;
* knowledge flow;
* compiler flow;
* persistence boundaries;
* projection boundaries;
* application entry points;
* external integration boundaries;
* subsystem maturity.

The resulting `vision/architecture-map.md` will serve as the primary orientation document for contributors who need to understand Monad's structure quickly before reading detailed specifications.

The map must clarify architecture without oversimplifying the distinctions established by the Manifesto, Principles, Laws, Glossary, and Ecosystem Overview.

---

# Problem Statement

The Monad ecosystem has a coherent textual architecture, but textual descriptions alone are insufficient for rapidly answering structural questions such as:

* Which layer owns a responsibility?
* What depends on what?
* Where does compilation stop and persistence begin?
* Where does canonical semantic knowledge exist?
* Which systems are projections rather than sources of truth?
* How do applications access the platform?
* Which components are implemented, specified, planned, or provisional?
* How do repository domains relate to runtime systems?

Without a canonical architecture map, contributors may create their own inconsistent diagrams or infer incorrect dependencies from repository layout.

That creates risks including:

* responsibility overlap;
* circular dependencies;
* compiler/kernel confusion;
* canonical/derived representation confusion;
* provisional systems being treated as implemented;
* repository directories being mistaken for runtime services;
* UI concerns leaking into foundational layers.

---

# Motivation

The Ecosystem Overview establishes the architecture in prose.

The Architecture Map must make that architecture inspectable at a glance.

It will provide:

* a stable system-context view;
* a layer map;
* a subsystem dependency map;
* a knowledge-flow view;
* a representation-boundary view;
* a repository-domain map;
* a maturity map;
* a legend defining how diagrams should be interpreted.

The map should become the common reference for:

* contributor onboarding;
* architecture reviews;
* work-packet planning;
* specification dependency analysis;
* documentation-site navigation;
* future system diagrams;
* AI context assembly.

---

# Objectives

This work packet has the following objectives:

1. Create one canonical architecture-map document.
2. Represent Monad's accepted architectural layers.
3. Place every accepted subsystem in one primary layer.
4. Show allowed dependency direction.
5. Show principal knowledge and compiler flows.
6. Distinguish source, compiler, semantic, persistent, lowered, and publication representations.
7. Distinguish runtime subsystems from repository knowledge domains.
8. Show application and external integration boundaries.
9. Display subsystem maturity honestly.
10. Define diagram conventions for later architecture artifacts.
11. Identify unresolved architectural boundaries without inventing solutions.
12. Provide a stable visual basis for the Compiler Pipeline and Knowledge Lifecycle documents.

---

# Required Outcome

At completion, a contributor should be able to answer the following using `vision/architecture-map.md`:

* Where does MSL live?
* What does MSC consume and produce?
* Is MSG a database?
* What does MKE persist?
* Where does KIR fit?
* Which systems produce publications?
* Where may AI participate?
* What is canonical versus derived?
* Which dependencies are forbidden?
* Which systems are current versus future?
* How does repository knowledge become semantic knowledge?
* Where do CLI, TUI, web, IDE, and agents belong?

The document must remain usable in plain Markdown without requiring a proprietary diagram tool.

# Required Document Structure

The Architecture Map should contain at least the following sections.

## 1. Purpose and Authority

Explain:

* what the map represents;
* what it does not represent;
* how conflicts with ADRs/specifications are resolved.

## 2. Reading the Map

Define:

* layer direction;
* dependency arrows;
* data/knowledge-flow arrows;
* maturity markers;
* boundary notation;
* canonical versus derived representation notation.

## 3. System Context

Show Monad in relation to:

* engineers;
* contributors;
* source repositories;
* external tools;
* AI providers;
* package ecosystems;
* CI/operations;
* publication audiences.

## 4. Layered Architecture

Map the accepted layers:

```text id="f0cpbr"
Layer 0 — Vision and Governance
Layer 1 — Knowledge Foundations
Layer 2 — Languages and Capture
Layer 3 — Compilation
Layer 4 — Semantic Representation
Layer 5 — Knowledge Kernel
Layer 6 — Knowledge Services and Projections
Layer 7 — Applications and Experiences
```

## 5. Core Dependency Map

Show:

```text id="cfz4tu"
MSL
  ↓
MSC
  ↓
MSG
  ↓
MKE
```

Then show derived paths:

```text id="nx1yh7"
MSG/MKE
  ├── KIR and backends
  ├── MPE and publications
  ├── MAE and AI context
  ├── search and analytics
  └── applications
```

The map must not imply that MKE is required for every in-memory compiler operation.

## 6. Canonical Representation Map

Show the progression and boundaries among:

* source artifact;
* surface AST;
* canonical AST;
* declaration and symbol state;
* resolved and analyzed semantic state;
* MSG;
* MKE graph history;
* KIR;
* publication projections;
* application views.

## 7. Compiler-to-Kernel Boundary

Clarify:

* MSC owns compilation;
* MSG is the handoff representation;
* MKE owns persistence and history;
* persistence failure does not redefine semantic compilation;
* MKE queries do not silently mutate compiler results.

## 8. Projection Boundary

Clarify:

* publications are projections;
* execution forms are projections;
* AI context is a projection;
* analytics are projections;
* projections may produce new evidence;
* new evidence must re-enter through explicit capture/compilation.

## 9. Repository Knowledge-Domain Map

Map:

* `vision/`;
* `adrs/`;
* `specifications/`;
* `engineering/`;
* `research/`;
* `journal/`;
* `knowledge/`;
* implementation directories.

Explicitly label this as repository organization, not runtime topology.

## 10. Application Access Map

Show how:

* CLI;
* TUI;
* web;
* IDE;
* agents;
* documentation site;
* APIs

access compilation, query, publication, and other services.

## 11. External Integration Map

Show integration categories and adapter boundaries.

## 12. Maturity Map

Mark each major subsystem as:

* implemented;
* partially implemented;
* specified;
* in specification;
* accepted;
* planned;
* provisional;
* reserved;
* deferred.

## 13. Forbidden Dependencies

List prohibited architectural edges.

## 14. Self-Hosting Path

Show staged self-hosting without implying current completion.

## 15. Map Invariants

State the conditions all future diagrams must preserve.

# Diagram Conventions

The deliverable must establish conventions such as:

## Arrow Types

| Notation | Meaning                                            |
| -------- | -------------------------------------------------- |
| `A → B`  | A produces, invokes, or directly supplies B        |
| `A ⇢ B`  | A may integrate with B through an adapter          |
| `A ⤳ B`  | B is a derived projection of A                     |
| `A ⊣ B`  | A constrains or governs B                          |
| `A ↔ B`  | Explicit bidirectional exchange; must be justified |

If Mermaid syntax limits visual distinction, labels must make semantics explicit.

## Boundary Types

| Boundary       | Meaning                          |
| -------------- | -------------------------------- |
| solid box      | accepted subsystem               |
| dashed box     | planned or provisional subsystem |
| double border  | canonical semantic boundary      |
| shaded group   | architectural layer              |
| external group | system outside Monad             |

## Maturity Markers

Recommended textual markers:

```text id="k3icec"
[IMPL] implemented
[PART] partially implemented
[SPEC] specified
[IN-SPEC] in specification
[ACPT] accepted
[PLAN] planned
[PROV] provisional
[RSVD] reserved
[DEFR] deferred
```

The document must include a legend and must not rely on color alone.

# Required Responsibility Map

The final document must preserve this responsibility model.

| Component    | Owns                                    | Must Not Own                                  |
| ------------ | --------------------------------------- | --------------------------------------------- |
| MSL          | expression of engineering knowledge     | compilation, persistence                      |
| MSC          | compilation and semantic construction   | historical persistence, publication ownership |
| MSG          | one semantic snapshot                   | storage engine, parsing                       |
| MKE          | persistent knowledge and history        | source-language semantics                     |
| MGO          | semantic vocabulary                     | one project's graph state                     |
| MPL          | publication intent                      | rendering                                     |
| MPE          | publication projection                  | canonical meaning                             |
| MAE          | AI context and assisted reasoning       | automatic authority                           |
| KIR          | lowered backend-oriented representation | canonical semantic truth                      |
| Applications | user interaction                        | foundational semantics                        |

# Architectural Impact

## Classification

**Architecture stabilization and visualization.**

This work packet should not introduce new architectural responsibilities.

It makes accepted architecture explicit, inspectable, and testable.

## Permitted Findings

The mapping process may identify:

* conflicting layer placement;
* overlapping responsibilities;
* unclear dependency direction;
* inconsistent maturity classification;
* missing canonical boundary;
* terminology mismatch.

Such findings must be recorded and resolved through:

* editorial correction;
* an existing work packet;
* an ADR where the change is significant;
* deferral where implementation evidence is required.

## Prohibited Actions

This work packet must not:

* invent new subsystem acronyms to simplify diagrams;
* collapse MSL, MSC, MSG, and MKE into one system;
* treat MKE as a compiler pass;
* depict MSG as a database implementation;
* treat KIR as canonical knowledge;
* depict MPE or MAE as required compiler dependencies;
* use repository folders as evidence of runtime service boundaries;
* hide provisional maturity in visual notation.

# Risks

## Risk 1 — Diagram-Driven Oversimplification

A compact diagram may erase important distinctions.

**Mitigation**

* Pair diagrams with precise explanatory text.
* Preserve canonical boundaries explicitly.

## Risk 2 — False Precision

The map may imply implementation decisions that have not been accepted.

**Mitigation**

* Keep deployment and process topology out of scope.
* Mark unresolved details as deferred.

## Risk 3 — Maturity Misrepresentation

Planned systems may visually appear complete.

**Mitigation**

* Use textual maturity markers.
* Include maturity in component labels.

## Risk 4 — Diagram Drift

Multiple later diagrams may contradict the canonical map.

**Mitigation**

* Declare this document the source for high-level architectural diagrams.
* Require later diagrams to reference or specialize it.

## Risk 5 — Tool Dependence

A diagram format may not render in all environments.

**Mitigation**

* Preserve plain-text equivalents.
* Keep Mermaid source directly in Markdown.

## Risk 6 — Architecture Expansion

Mapping may become another opportunity to invent systems.

**Mitigation**

* Map accepted architecture only.
* Record unresolved ideas separately.
